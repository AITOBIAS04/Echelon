## 1. Problem Statement

Three backend gaps block the next honest pass on Echelon's operational layer:

### 1.1 Agent Deployment Has No Backend

The frontend `DeployAgentModal.tsx` treats deployment as "mint a new organism" — it asks for archetype, callsign, and mock theatres. The correct contract is "assign an existing roster agent to a theatre and activate its strategy there." The backend has:

- A seeded agent roster (`data/seed/seed_v2.sql`, `backend/api/agents_routes.py`)
- An `Agent` model with archetype, sanity, P&L, genome, parent_agent_ids
- A separate breeding system (`backend/genealogy_manager.py`) that is in-memory
- **No `agent_deployments` table** — no persisted record of which agent is assigned to which theatre
- **No deployment CRUD endpoints** — no way to create, list, or withdraw deployments
- **No strategy profile persistence** — Balanced/Aggressive/Defensive exists only in frontend mock

### 1.2 Investigations Are Not Persisted

The investigation toolset (`backend/investigation/`) is fully functional with 8 tools (Signal Scanner, Entity Resolver, Evidence Envelope, Corroboration Checker, Counter-Signal Feed, Claim Graph, Commitment Monitor, Certificate Builder). The API contract is stable. The frontend is fully wired. But:

- **All state is in a process-local dict** — investigations are lost on restart
- **No SQLAlchemy models** for Investigation, EvidenceItem, ClaimNode, CounterSignal, DriftEvent
- **No Alembic migration** for investigation tables
- The API routes note: "Persistence status: DEFERRED (Cycle 014c scope)"

### 1.3 Theatres Don't Surface Paradox Risk

The paradox detection engine (`backend/worker/tasks/paradox.py`) computes logic gaps, stability thresholds, and spawns paradoxes. The evidence service (`backend/services/evidence_service.py`) has inquiry-class-aware validation rules. But:

- **No computed `paradox_risk` field** on theatre or timeline responses
- **No inquiry-class-aware risk weighting** exposed to API consumers
- **No risk explanation model** (logic gap, counter-signals, evidence freshness, stability)

## 2. Product Contracts

### 2.1 Agent Deployment

**Deploy Agent** = assign an existing roster agent to a theatre and activate its strategy there. Not "mint a new organism."

**Breed Agent** = separate advanced flow for offspring creation from two eligible parents. Not in this cycle.

**Genesis Agents** = seeded platform identities. Already exist in the roster.

Product split:
- Normal user action: deploy an agent
- Advanced creation action: breed an agent (future cycle)
- Platform bootstrap: genesis agents already exist

### 2.2 Fleet vs Agent Detail

Fleet table stays operational: name, archetype, status, deployed theatres, last action, P&L, intervention actions. No genealogy column.

Agent Detail owns lineage depth: generation, parents, offspring, inherited traits, mutation history, genome hash, breeding eligibility/cooldown/points. This is future frontend work (Alexander).

### 2.3 Paradox Risk Language

Theatre surfaces expose `Paradox Risk: Low / Watch / High`. Never "fake market."

User-facing explanations:
- Evidence weak
- Counter-signals rising
- Logic gap widening
- Stale investigation
- Paradox active

Inquiry-class weighting:
- **COUNTERFACTUAL:** market-vs-signal divergence, stability
- **INVESTIGATIVE:** evidence weakness, corroboration gaps, contradictory evidence, freshness
- **INSPECTION:** unmet criteria, criteria contradiction
- **SURVEY:** thin participation, distorted sampling
- **SCRUTINY:** highest sensitivity to adversarial contradiction, counter-signals

## 7. API Changes

### New Endpoints

- `POST /api/v1/agent-deployments` — create deployment
- `GET /api/v1/agent-deployments` — list deployments (filter by agent_id, theatre_id, status)
- `GET /api/v1/agent-deployments/{id}` — deployment detail with audit trail

- `POST /api/v1/agent-deployments/{id}/pause` — pause deployment
- `POST /api/v1/agent-deployments/{id}/resume` — resume deployment

### Extended Responses

- `GET /api/v1/agents/{id}` — +`active_deployments_count`, +`active_deployments` (list of summaries)
- `GET /api/v1/agents` — +`active_deployments_count` per agent (count only for list performance)
- `GET /api/v1/theatres/{id}` — +`paradox_risk` object (level, factors, explanation)
- `GET /api/v1/theatres` — +`paradox_risk_level` summary field per theatre

### Investigation Routes (Unchanged Contract)

All existing investigation endpoints keep the same request/response shapes. The only change is internal: persistence backend swapped from process-local dict to SQLAlchemy repository.

## 10. NFRs

1. **Separation of concerns:** Agent deployment is its own service and route file. Do not merge into agents_routes.py.
2. **Investigation API stability:** Existing request/response shapes must not change. The persistence swap is invisible to API consumers.
3. **Backwards compatibility:** All existing investigation toolset tests must continue passing. The in-memory toolset classes remain functional — the repository layer wraps them.
4. **Deployment guards:** Cannot deploy a dead agent. Cannot deploy to a non-deployable theatre. Cannot deploy to an uncertified theatre. Cannot have two active deployments of the same agent to the same theatre.
5. **Paradox risk vocabulary:** API responses use `LOW`, `WATCH`, `HIGH` — not "fake", "suspicious", "dangerous".
6. **Audit trail:** All deployment state transitions logged as audit events (mirrors TheatreAuditEvent pattern).
