### 1.1 Data Flow

**Deployment operations**

```text
Agent deployment lifecycle event
  -> DeploymentTelemetryService builds summary state
  -> DeploymentInterventionService records action + audit
  -> Agent/deployment responses expose operational state
  -> DEPLOYMENT_STATUS_CHANGED or DEPLOYMENT_INTERVENTION_REQUIRED emitted
```

**Investigation intelligence**

```text
Signal scan or manual signal intake
  -> InvestigationSignalIngestor validates domain filters + registry policy
  -> signal persisted with provenance
  -> InvestigationEntityEnricher resolves entity context if applicable
  -> StopConditionOrchestrator evaluates material status changes
  -> InvestigationReadinessService updates READY / ANCHORED / ISSUED state
  -> investigation WS events emitted as needed
```

## 3. Sprint 1 — Deployment Summaries + Intervention API

### 3.1 DeploymentTelemetryService

**New file:** `backend/services/deployment_telemetry_service.py`

Responsibilities:

- summarize deployment state for Fleet
- compute latest activity / heartbeat-like state from available runtime signals
- normalize deployment display fields for agent and deployment responses

### 3.2 DeploymentInterventionService

**New file:** `backend/services/deployment_intervention_service.py`

Responsibilities:

- wrap pause/resume/withdraw/strategy change operations
- require actor identity and reason where appropriate
- create structured audit events

Suggested audit detail payload:

```json
{
  "old_status": "ACTIVE",
  "new_status": "PAUSED",
  "actor_id": "user_123",
  "reason": "manual risk review"
}
```

### 3.3 Response Integration

Update:

- `GET /api/v1/agents`
- `GET /api/v1/agents/{id}`
- `GET /api/v1/agent-deployments`
- `GET /api/v1/agent-deployments/{id}`

Use shared summary-building logic to avoid response drift.

## 4. Sprint 2 — Live Signal Scanner Intake

### 4.1 InvestigationSignalIngestor

**New file:** `backend/services/investigation_signal_ingestor.py`

Responsibilities:

- call supported collector surfaces only
- enforce domain-filter commitment
- enforce source-registry policy fields
- persist scanner output with provenance/receipt context

### 4.2 Domain Filter Enforcement

Committed domain filters are part of the investigation contract.

At ingestion time:

- source/category must map to a committed domain
- out-of-scope signals must be rejected or explicitly flagged
- acceptance path must never silently widen the inquiry scope

### 4.3 Registry Policy Enforcement

Scanner-backed signals must respect:

- `query_determinism`
- `receipt_body_required`
- `requires_legal_review`

Signals that violate registry policy should not be treated as cleanly admissible.

## 5. Sprint 3 — Entity Resolver + Evidence Enrichment

### 5.1 InvestigationEntityEnricher

**New file:** `backend/services/investigation_entity_enricher.py`

Responsibilities:

- resolve entity context for evidence items and claims
- cache/bound persistence of resolved profiles
- link evidence to resolved entities

### 5.2 Persistence Strategy

Prefer bounded enrichment persistence:

- cache key derived from normalized lookup input
- store source references and resolution timestamp
- avoid creating a general-purpose graph platform in this cycle

### 5.3 API Posture

Add enrichment context additively:

- do not break stable investigation routes
- add enriched context only where it can fit existing models cleanly
- otherwise use additive endpoints or optional fields

## 6. Sprint 4 — Stop Condition Orchestration + Certificate Readiness

### 6.1 StopConditionOrchestrator

**New file:** `backend/services/stop_condition_orchestrator.py`

Responsibilities:

- evaluate stop conditions after material mutations
- record stop-condition status and reasons
- hand off readiness decision to readiness service

Mutation inputs:

- evidence submission
- claim status change
- material counter-signal
- drift event

### 6.2 Drift-Aware Routing Impact

Material Commitment Monitor drift is a first-class signal.

It can:

- block automatic issuance
- force `REVIEW_REQUIRED`
- appear in readiness reasons even if outcome resolution would otherwise pass

### 6.3 InvestigationReadinessService

**New file:** `backend/services/investigation_readiness_service.py`

Responsibilities:

- maintain `READY`, `ANCHORED`, `ISSUED`, `NOT_READY`
- separate readiness from final issuance
- respect daily batch anchoring

Suggested transition model:

```text
ACTIVE -> READY -> ANCHORED -> ISSUED
ACTIVE -> NOT_READY (default / after blocking condition)
READY -> NOT_READY (if new drift/counter-signal invalidates readiness)
```

### 6.4 Daily Batch Anchor Rule

The v1 default from the design note is a daily batch anchor at `00:00 UTC`.

Implementation consequences:

- `issued_at` is not set at readiness time
- a certificate can be READY for hours before anchor
- anchoring is a real lifecycle step, not a metadata afterthought

## 7. Sprint 5 — WebSocket Events + Integration

### 7.1 Deployment Events

Support:

- `DEPLOYMENT_STATUS_CHANGED`
- `DEPLOYMENT_INTERVENTION_REQUIRED`

### 7.2 Investigation Events

Support:

- `INVESTIGATION_SIGNAL_INGESTED`
- `INVESTIGATION_STOP_CONDITION_MET`
- `INVESTIGATION_CERTIFICATE_READY`

### 7.3 Integration Paths

Required paths:

1. deployment operational flow:
   - create deployment
   - pause/resume
   - strategy change
   - withdraw
   - audit/events remain coherent

2. investigation operational flow:
   - create/load investigation
   - ingest signal under committed domain filters
   - enrich evidence/entity context
   - stop condition met
   - readiness recorded
   - batch anchor transition
   - issuance finalised

## 8. API Changes

### 8.1 Deployment

- `GET /api/v1/agent-deployments` — operational summary fields
- `GET /api/v1/agent-deployments/{id}` — intervention history + latest activity
- `POST /api/v1/agent-deployments/{id}/pause` — require reason
- `POST /api/v1/agent-deployments/{id}/resume` — require actor identity
- `POST /api/v1/agent-deployments/{id}/strategy` — require old/new strategy + reason persistence

### 8.2 Agent Responses

- `GET /api/v1/agents` — retain count, add lightweight deployment summaries if needed for Fleet
- `GET /api/v1/agents/{id}` — richer summaries for Agent Detail

### 8.3 Investigation

Prefer additive endpoints:

- `GET /api/v1/investigations/{id}/readiness`
- `POST /api/v1/investigations/{id}/scan`
- `POST /api/v1/investigations/{id}/finalise`
