## 1. Problem Statement

Cycle 019 made deployments and investigations durable. That is necessary, but not sufficient for release.

### 1.1 Deployment Exists But Is Not Yet Fully Operational

The backend now has persisted `agent_deployments`, guards, and basic lifecycle controls. But Fleet and Agent Detail still lack a fully operational backend contract:

- deployment summaries are still thin
- intervention actions are not yet the primary operational surface
- last activity / telemetry context is not consistently exposed
- deployment state changes are not yet rich enough for frontend release usage

### 1.2 Investigation Persistence Exists But Live Intelligence Intake Is Still Thin

The investigation toolset now survives restart and persists evidence, claims, signals, drift, and certificates. But the product is intended to be a bounded inquiry workspace, not just a record store:

- Signal Scanner is not yet a real live intake path for release
- committed domain filters are not yet the primary enforcement surface for ingestion
- entity enrichment is not yet operationally useful
- stop conditions and certificate readiness are not yet fully orchestrated

### 1.3 Certificate Finalisation Still Needs Release-Grade Orchestration

The design note distinguishes:

- `READY`
- `ANCHORED`
- `ISSUED`

That distinction matters. Stop conditions, drift events, and anchor timing all affect whether a certificate should move forward. The release backend needs:

- automatic stop-condition evaluation
- drift-aware readiness reasoning
- daily batch anchoring semantics
- clear separation between readiness and issuance

### 1.4 Dependency Chain Needs Explicit Discipline

Cycle 021 depends on:

- investigation tooling from 014c
- live collector surfaces from 015
- policy/routing logic from 017
- deployment/investigation persistence from 019
- paradox orchestration from 020

That chain is acceptable, but only with an explicit health gate at the start of execution.

## 2. Product Contracts

### 2.1 Agent Deployment Is An Operational Surface

Deployments are not just rows. The backend must provide:

- deployment summaries suitable for Fleet
- intervention history and current intervention state
- theatre-linked context
- actor-attributed auditability

Fleet remains operational. Genealogy remains out of scope.

### 2.2 Investigation Scope Is Committed

Domain filters chosen at investigation creation are binding:

- they contribute to the commitment hash
- they constrain live signal ingestion
- they are recorded in the certificate

Signals from outside the committed domain scope must not be silently ingested into the investigation record.

### 2.3 Stop Conditions Are Live

Stop-condition evaluation must react to material investigation changes, including:

- evidence submission
- claim status change
- material counter-signal ingestion
- drift events

Material drift is not just another event. It can force `REVIEW_REQUIRED` even when the nominal outcome appears resolved.

### 2.4 Certificate Finalisation Is Multi-Stage

The release contract is:

- `READY` = inquiry satisfies stop-condition/readiness criteria
- `ANCHORED` = included in the daily batch anchor
- `ISSUED` = final certificate issued with `issued_at`

The v1 daily batch anchor at `00:00 UTC` must be respected.

## 7. API Changes

### Deployment

- `GET /api/v1/agent-deployments` — include operational summary fields
- `GET /api/v1/agent-deployments/{id}` — include intervention history + latest activity summary
- `POST /api/v1/agent-deployments/{id}/pause` — require reason
- `POST /api/v1/agent-deployments/{id}/resume` — require actor identity
- `POST /api/v1/agent-deployments/{id}/strategy` — persist old/new strategy + reason

### Agent Responses

- `GET /api/v1/agents` — retain `active_deployments_count`, optionally add lightweight deployment summary fields needed for Fleet
- `GET /api/v1/agents/{id}` — include richer deployment summaries suitable for Agent Detail

### Investigation

Prefer additive endpoints over breaking the existing stable route contract.

Likely additive endpoints:

- `GET /api/v1/investigations/{id}/readiness`
- `POST /api/v1/investigations/{id}/scan`
- `POST /api/v1/investigations/{id}/finalise`

## 8. WebSocket Event Additions

| Event Type | Trigger | Payload |
|------------|---------|---------|
| `DEPLOYMENT_STATUS_CHANGED` | Deployment transitions ACTIVE/PAUSED/WITHDRAWN | deployment_id, agent_id, theatre_id, old_status, new_status |
| `DEPLOYMENT_INTERVENTION_REQUIRED` | Deployment enters blocked/degraded/manual-review state | deployment_id, agent_id, theatre_id, reason |
| `INVESTIGATION_SIGNAL_INGESTED` | Scanner/manual path adds signal | investigation_id, signal_id, signal_class, material |
| `INVESTIGATION_STOP_CONDITION_MET` | Stop condition evaluator marks inquiry ready to stop | investigation_id, stop_condition, reason |
| `INVESTIGATION_CERTIFICATE_READY` | Investigation becomes READY, ANCHORED, or ISSUED | investigation_id, certificate_id, status |
